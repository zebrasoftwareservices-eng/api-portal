# Research brief — production install

Spec 016 (JSO-244). Evidence for the product manager. This is not a spec.

## Question

A platform engineer who already runs Kong needs to install this portal on a company server, back it up, and upgrade it without losing data, using a guide that finishes on a clean Linux VM in under 30 minutes.

## Sources

Each fact below is from a page opened for this brief, or from the repo files named here.

**How similar products split evaluation and production**

- [Tyk install](https://tyk.io/docs/tyk-self-managed/tyk-helm-chart/): Docker is the recommended path for development, testing, and proof of concept. Kubernetes is listed as a separate install. Tyk 5.x tests PostgreSQL 15 through 18. Redis is required for the gateway, and Tyk says to make Redis highly available in production. Air-gapped install is its own guide.
- [Gravitee on Kubernetes](https://documentation.gravitee.io/apim/self-hosted-installation-guides/kubernetes): the Helm chart requires Kubernetes 1.14 or later and does not set an upper bound. Chart version and `appVersion` match, so pinning the chart pins the images. Gravitee says not to use the `latest` tag: the default pull policy is `Always`, a restart can pull a newer image, and data migrations are forward-only, so that upgrade cannot be reversed. Their component containers run as non-root. Probes, resources, and ingress annotations are values, not a second product. Cert-manager and cluster-specific ingress controllers are the operator's.
- [Kong Helm chart](https://github.com/Kong/charts/blob/main/charts/kong/README.md): the chart's Postgres sub-chart is for temporary environments. For longer-lived installs Kong says to run the database outside the release. From chart 3.0 the operator must name the Postgres image, because the Bitnami images are no longer maintained. Kong's own chart is the gateway, not a developer portal. Bundled Postgres is the wrong model for a portal a company keeps.
- [WSO2 API Portal production deployment](https://wso2.com/bijira/docs/api-portal/1.0.0/deployment/overview/): production is the portal plus a database. The gateway stays outside the deployment. The chart ships a Service, not an Ingress; the operator brings the load balancer or ingress and sets the public base URL, because the portal cannot infer it behind a proxy. A single instance is a supported deployment. High availability is extra: an external database, the same encryption key and session secret on every instance, and instances in different failure domains. The quick start is called out as the wrong shape for production.

- `docs/product-brief.md`: each company installs its own portal. Compose is today's path. The Helm chart is v0.8. Distribution is GitHub, Docker images, and a Helm chart. Marketplace listings are later. There is no multi-tenant hosting.
- `docs/roadmap.md` sprint 7: install on a clean Linux VM from the guide in under 30 minutes, upgrade from v0.7 keeps data, and the Helm chart passes a CI smoke test. Elango decides the support matrix.

Sample data is opt-in with `SEED_SAMPLE=true`. The default install creates no admin, API, consumer, key, route, or service. `ADMIN_EMAIL` and `ADMIN_PASSWORD` skip the wizard. The hosted demo's backup and recovery live in `deploy/hosted/README.md`.
- `gh repo view zebrasoftwareservices-eng/api-portal`: the repository is private. `gh release list` returned no releases. `.github/workflows/` contains `ci.yml` only.

## Fits one pull request

**Build in spec 016.** Three install paths, written down in one ADR. The quickstart stays the evaluation path and is not replaced.

1. **Production Compose, separate from the quickstart and from `deploy/hosted/`.** It pulls pinned images, sets `NODE_ENV=production`, takes secrets from an env file or from files, does not seed the sample API, and does not publish Postgres or the server on the host. TLS ends at a reverse proxy the guide shows (one Caddy or nginx example). The portal does not terminate TLS itself. Kong is not in this file. The guide points at a Kong the company already runs, using the spec 005 environment variables and `docs/connect-kong.md`.
2. **Versioned images on GHCR.** Publish the server and portal images on a version tag, never as `latest`. The 30-minute guide pulls those tags. It does not clone the repo and build. CI proves an upgrade by starting the previous tag, writing data, starting the new tag against the same volume, and checking the data is still there. Migrations stay forward-only.
3. **Backup, restore, and rollback.** A logical Postgres dump and a restore command. Rollback is: stop, restore that dump, start the previous image tag. Say that in the guide. Do not add down migrations. Gravitee documents the same limit: a newer process applies migrations that `helm rollback` does not undo.
4. **Helm chart.** Portal, server, and Postgres. Postgres can be the chart's database for the CI smoke test and a small install, with an external database URL for a company that already runs PostgreSQL. Probes use the existing health check plus a readiness check that fails when the database is down. One replica by default. Containers run as non-root. The chart does not install Kong, cert-manager, or an ingress controller. Ingress is optional values. The public URL is a required value when a proxy is in front, matching WSO2's base-URL rule.
5. **JSO-378, because Elango already assigned it here.** One setup token shared by every server replica while no admin exists (a single database row or one Secret the chart mounts). A token read from any replica's logs works on any replica. Default `replicaCount` stays 1. Do not add a pod disruption budget, autoscaling, or a multi-zone topology.
6. **CI.** A throwaway Kubernetes cluster (kind or the same) installs the chart and hits readiness. That is the Friday Helm demo. The user-tester follows the VM guide. CI does not boot a cloud VM.

**Leave in place.**

- `deploy/docker-compose.yml` and the five-minute quickstart, including the bundled Kong and optional sample.
- `deploy/hosted/` — the ZSS demo, its Caddy, and its reset timer.
- Spec 005's wizard, env-managed gateway, and single-admin claim. This spec only makes the production token the same on every replica.

**Split out.**

- High availability: several portal replicas as a supported topology, an external highly available Postgres as a requirement, PodDisruptionBudgets, autoscaling. WSO2 treats a single instance as legitimate and HA as extra. The chart may allow an external database URL without promising failover.
- Installing or upgrading the company's Kong. Kong's chart already does that.
- cert-manager, Vault, external-secrets, OpenShift, air-gapped mirrors, Windows, and marketplace listings. Tyk documents air-gap and marketplaces separately. The product brief leaves AWS and Google Cloud marketplace listings until after GitHub, images, and Helm.
- Replacing the demo backup. Spec 006 keeps the reset.

## Open questions for Elango

- [ ] **Support matrix.** Recommend one OS in the guide: Ubuntu 26.04 LTS, Docker Engine with Compose v2. Recommend one Kubernetes minor, the one the CI cluster runs, declared as the chart's `kubeVersion`, plus Helm 3. Recommend PostgreSQL 17, the major spec 005's tests already use. 24.04 LTS can be named as "expected to work" without a second walkthrough.
- [ ] **Public images.** The GitHub repo is private, and there are no releases. A company cannot follow a 30-minute pull-based guide until the packages are public. Spec 002's decision was to make the repo public. Confirm that GHCR images for this install are public, and whether that waits on making the repo public.
- [ ] **Rollback.** Confirm rollback means restore the logical backup and run the previous image tag. No down migrations.
- [ ] **Kong in the production Compose file.** Recommend no. Evaluation keeps the bundled Kong. Production connects to the company's Kong. Confirm.
