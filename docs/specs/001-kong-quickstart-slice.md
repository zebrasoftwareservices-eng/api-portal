# 001 — Kong quickstart: from OpenAPI spec to a working API key

## Summary
A platform engineer runs one command and gets a portal where a developer can read API docs,
sign up, create an app, receive a Kong API key, and make a successful call from the browser.

## Problem
Kong Gateway OSS has no self-serve developer portal. Teams hand out keys manually through
the Admin API or build their own portal. This slice proves the whole loop end to end and
becomes the project's demo and quickstart.

## Users
Platform engineer (installs and publishes), API consumer (developer who signs up and calls the API).

## User stories
- As a platform engineer, I want to start the portal and a Kong gateway with one command,
  so that I can evaluate the project in minutes.
- As a platform engineer, I want to import an OpenAPI spec and link it to a Kong service,
  so that its docs appear in the portal.
- As a developer, I want to sign up, create an app and get an API key,
  so that I can call the API without emailing anyone.
- As a developer, I want to try a request from the docs page with my key,
  so that I know my key works before writing code.

## Acceptance criteria
1. **Given** Docker is installed **When** the engineer runs `docker compose -f deploy/docker-compose.yml up`
   **Then** the portal, server, Postgres and Kong start, and the portal home page loads at
   `http://localhost:3000` within 5 minutes on a typical laptop.
2. **Given** the quickstart is running **When** it starts for the first time
   **Then** a sample API (OpenAPI 3.x spec plus a matching Kong service and route with the
   key-auth plugin) is seeded and published.
3. **Given** an admin is signed in **When** they import an OpenAPI 3.x file or URL and link it to a
   Kong service **Then** the API reference appears in the public catalog.
4. **Given** an invalid OpenAPI file **When** the admin imports it **Then** the import is rejected
   with a message naming the first validation error, and nothing is published.
5. **Given** a visitor **When** they sign up with email and password **Then** they reach their
   developer dashboard signed in.
6. **Given** a signed-in developer **When** they create an app and subscribe it to the sample API
   **Then** a Kong consumer and key-auth credential are created, tagged with the portal app ID,
   and the key is shown once with a copy button.
7. **Given** a developer with a key **When** they use the try-it console on an operation
   **Then** the request goes through Kong and the response is shown; without a key, Kong's 401 is shown.
8. **Given** Kong's Admin API is unreachable **When** a developer creates an app
   **Then** they see a clear "gateway unavailable, try again" error, no partial app is left,
   and a retry later succeeds without duplicate Kong consumers.
9. **Given** a developer revokes a key **When** they call the API with it **Then** Kong returns 401.

## Out of scope
- AWS API Gateway (spec 002), other gateways
- SSO / OIDC, teams and orgs, approval workflows
- Page builder, custom widgets, theming beyond the default theme
- Rate-limit plans, analytics, MCP server, AI features
- Helm chart (later spec)

### Runtime topology (`deploy/docker-compose.yml`)
| Service | Image | Ports (host) | Notes |
| --- | --- | --- | --- |
| `postgres` | `postgres:17-alpine` | none | Two databases, `portal` and `kong` (init script); healthcheck `pg_isready` |
| `kong-migrations` | `kong:3.9` | none | `kong migrations bootstrap`, runs once and exits |
| `kong` | `kong:3.9` | `8000` proxy; `127.0.0.1:8001` admin | `KONG_DATABASE=postgres`; healthcheck `kong health` |
| `httpbin` | `mccutchen/go-httpbin:v2.15.0` | none | Upstream for the sample API (~10 MB image) |
| `server` | `portal-server` (build `apps/server/Dockerfile`) | `4000` | depends_on postgres healthy, kong healthy; healthcheck `GET /api/v1/health` |
| `portal` | `portal-web` (build `apps/portal/Dockerfile`, Next.js `output: standalone`) | `3000` | depends_on server healthy; rewrites `/api/:path*` → `http://server:4000/api/:path*` |

Each app service has both `image:` and `build:`. Once CI publishes images to GHCR, `up` pulls
them; until then it builds them. The server image runs migrations at start under a Postgres
advisory lock, so there's no separate migration container.

The `portal` container runs a small ingress (`apps/portal/ingress`, JSO-169) on port `3000`,
in front of Next.js on `127.0.0.1:NEXT_INTERNAL_PORT` (default `PORT + 1`). The ingress replaces
all caller-supplied forwarding headers with the socket peer address. The server trusts only the
address that `PORTAL_PROXY_HOST` resolves to (`portal`, set in the compose file; default
`localhost`), and only one hop, so try-it budgets are per client.
A reverse proxy in front of the portal counts as one client (follow-up JSO-187).

Server environment (all in `deploy/.env.example`; compose ships dev defaults marked INSECURE):
`DATABASE_URL`, `BETTER_AUTH_SECRET`, `PORTAL_ENCRYPTION_KEY` (32 bytes base64; AES-256-GCM
for gateway admin tokens), `PORTAL_PUBLIC_URL` (`http://localhost:3000`), `KONG_ADMIN_URL`
(`http://kong:8001`), `KONG_ADMIN_TOKEN` (optional; for Kong behind an auth proxy),
`KONG_PROXY_INTERNAL_URL` (`http://kong:8000`), `KONG_PROXY_PUBLIC_URL` (`http://localhost:8000`),
`ADMIN_EMAIL` / `ADMIN_PASSWORD` (`admin@example.com` / `change-me-now`), `SEED_SAMPLE` (`true`).
If `NODE_ENV=production` and any secret still has its dev default, the server refuses to start.

**Startup sequence (server).** It's idempotent and every step is safe to re-run:
1. `migrate()` (advisory lock).
2. Ensure the `instance_settings` row exists (generate `instance_id` once).
3. Upsert the `gateways` row `default` from the `KONG_*` env vars (admin token encrypted).
4. If no user has `role = admin`, create one from `ADMIN_EMAIL` and `ADMIN_PASSWORD`, and log
   "admin created: <email>". Never log the password.
5. If `SEED_SAMPLE=true`, seed the sample API (below).
6. Start pg-boss and schedule `gateway-reconcile` (every 5 minutes, plus one run now).
7. Listen on `:4000`.

If Kong isn't reachable during step 5, log a warning and retry from the pg-boss job
(`seed-sample`, with backoff) instead of failing the boot.

**Sample seed (AC 2).** `apps/server/seed/sample-api.openapi.yaml` is an OpenAPI 3.1 "Sample
HTTP API" covering go-httpbin's `GET /get`, `POST /post`, `GET /status/{code}`, `GET /uuid` and
`GET /headers`, with an `apiKey` scheme (`header: apikey`). Kong objects are written with PUT so
re-running converges:
- `PUT /services/portal-sample` with `url: http://httpbin:8080` and the portal tags.
- `PUT /routes/portal-sample` with `service.name: portal-sample`, `paths: ["/sample"]`,
  `strip_path: true` and the tags.
- `PUT /plugins/{fixed UUID}` with `name: key-auth`, `service.name: portal-sample` and
  `config.key_names: ["apikey"]`.

Then it upserts `apis` slug `sample`, linked to `portal-sample`, `route_path: /sample`,
published. Tags are `portal`, `portal-instance-<id>` and `portal-seed`.

### API contract
Full contract: `apps/server/openapi.yaml` (OpenAPI 3.1, linted with Redocly). The server serves
under `/api`, and the portal's Next.js rewrite makes every browser call same-origin. Better
Auth owns `/api/auth/*`. Use its standard email routes (`/sign-up/email`, `/sign-in/email`,
`/sign-out`, `/get-session`) and set `autoSignIn: true` with no email verification in this slice.

| Method & path | Auth | Purpose | AC |
| --- | --- | --- | --- |
| `GET /v1/health` | public | Server status and Kong reachability | 1 |
| `GET /v1/apis` | public | Catalog list | 2, 3 |
| `GET /v1/apis/{slug}` | public | API detail | 3 |
| `GET /v1/apis/{slug}/openapi.json` | public | Document for Scalar: `servers` → public gateway base URL; `portalApiKey` scheme injected if there's no apiKey scheme | 3, 7 |
| `GET /v1/me` | session | Current user and role | 5 |
| `GET /v1/apps` · `POST /v1/apps` | session | List apps · create app + subscriptions + first key (key returned once) | 6, 8 |
| `GET /v1/apps/{appId}` | session (owner) | App with subscriptions and key hints | 6, 9 |
| `POST /v1/apps/{appId}/credentials` | session (owner) | Issue another key (max 5 active) | 9 |
| `DELETE /v1/apps/{appId}/credentials/{credentialId}` | session (owner) | Revoke key (idempotent) | 9 |
| `GET /v1/admin/gateway/services` | admin | Kong services + routes + key-auth flag, for the link picker | 3 |
| `POST /v1/admin/apis` | admin | Import `{spec: {url} or {content}, gatewayServiceId, slug?, routePath?}`, validate, publish | 3, 4 |
| `GET/POST/PUT/PATCH/DELETE /v1/try-it?scalar_url=` | public, rate-limited | Try-it proxy (ADR 0003) | 7 |

Error cases, all `application/problem+json` with a relative `type`:
- `400 /problems/validation`
- `401 /problems/unauthenticated`
- `403 /problems/forbidden`
- `404 /problems/not-found`. This is also returned for another developer's app, so app IDs
  don't leak.
- `409 /problems/app-name-taken`, `/problems/api-slug-taken`, `/problems/credential-limit`
- `413 /problems/document-too-large` (over 5 MiB) or `/problems/payload-too-large`
- `422 /problems/invalid-openapi`
  - `detail` = "Invalid OpenAPI document: <first error message> at <pointer>"
  - `errors` = `[first error]` (AC 4)
- `422 /problems/unsupported-openapi-version`, `/problems/spec-url-unreachable`,
  `/problems/gateway-service-not-found`, `/problems/gateway-service-has-no-route`
- `429 /problems/rate-limited`
- `502 /problems/gateway-rejected`
- `503 /problems/gateway-unavailable`, with `Retry-After: 5` and
  `detail` = "The API gateway didn't respond. Nothing was created. Try again in a moment." (AC 8)
- `504 /problems/try-it-timeout`

Import rules:
- The document must be OpenAPI `3.0.x` or `3.1.x`.
- External `$ref`s are bundled with `@scalar/openapi-parser`. Remote refs are allowed only when
  importing by URL, and only to the same host.
- `spec.url` fetch: http(s) only, 10 s timeout, 5 MiB cap, at most 3 redirects. It's admin-only,
  so SSRF exposure is limited to admins. This is noted as a risk.
- Default slug comes from `info.title`.
- The stored document is the bundled JSON; the original `servers` are kept in storage but replaced when served.

### Data model (`packages/db`, Drizzle; migration `0000_init`)
All IDs are `uuid` (UUIDv7 generated in the app) and timestamps are `timestamptz` (UTC).
Better Auth is configured to use UUIDv7 IDs (`advanced.database.generateId`), and its
tables are generated with the Better Auth CLI and committed alongside ours.

| Table | Columns | Constraints |
| --- | --- | --- |
| `user`, `session`, `account`, `verification` | Better Auth defaults; `user.role text not null default 'developer'` (additional field, `input: false` so sign-up can't set it) | `user.email` unique; check `role in ('developer','admin')` |
| `instance_settings` | `id smallint pk default 1`, `instance_id uuid not null`, `created_at` | check `id = 1` |
| `gateways` | `id`, `name text`, `kind text`, `admin_url text`, `admin_token_ciphertext text null`, `proxy_public_url text`, `proxy_internal_url text`, `created_at`, `updated_at` | `name` unique; check `kind in ('kong')` |
| `apis` | `id`, `slug text`, `title text`, `version text`, `description text null`, `gateway_id fk`, `gateway_service_id text`, `gateway_service_name text`, `route_path text`, `document jsonb`, `source_url text null`, `created_by fk user null`, `published_at`, `created_at`, `updated_at` | `slug` unique; index `(published_at desc)` |
| `apps` | `id`, `owner_id fk user on delete cascade`, `name text`, `description text null`, `created_at`, `updated_at` | unique `(owner_id, name)` |
| `subscriptions` | `id`, `app_id fk on delete cascade`, `api_id fk on delete restrict`, `created_at` | unique `(app_id, api_id)` |
| `gateway_consumers` | `id`, `app_id fk on delete cascade`, `gateway_id fk`, `external_id text` (Kong consumer id), `username text`, `created_at` | unique `(app_id, gateway_id)` |
| `credentials` | `id` (also the Kong key-auth id), `app_id fk on delete cascade`, `gateway_id fk`, `kind text default 'api-key'`, `key_hint text`, `status text`, `created_at`, `revoked_at null` | check `status in ('active','revoked')`; index `(app_id, status)` |

The key itself is never stored. `key_hint` holds the last 4 characters.

### Gateway adapter calls (Kong Admin API, ADR 0002)
Every call uses a 5 s timeout and has no retries in the request path. Network errors, timeouts
and 5xx become `GatewayUnavailableError`. Other 4xx become `GatewayRejectedError`. A 404 on
DELETE counts as success. Tags on every object: `portal`, `portal-instance-<instanceId>`,
`portal-app-<appId>`, plus `portal-cred-<credId>` on credentials.

| Adapter method | Kong call | Idempotency |
| --- | --- | --- |
| `health()` | `GET /status` (+ `GET /` for version) | read |
| `listServices()` | `GET /services?size=1000` (follow `next`), `GET /routes?size=1000`, `GET /plugins?size=1000` filtered to `key-auth` | read |
| `getService(idOrName)` | `GET /services/{idOrName}` (+ its routes and plugins) | read; 404 → `null` |
| `ensureConsumer(app)` | `PUT /consumers/portal-app-<appId>` `{username, custom_id: appId, tags}` | upsert by username |
| `issueCredential(app, {id, key})` | `PUT /consumers/portal-app-<appId>/key-auth/<credId>` `{key, tags}` | upsert by portal credential id |
| `revokeCredential(app, credId)` | `DELETE /consumers/portal-app-<appId>/key-auth/<credId>` | 404 = ok |
| `deleteConsumer(app)` | `DELETE /consumers/portal-app-<appId>` (cascades key-auth) | 404 = ok |
| `listOwnedConsumers()` | `GET /consumers?tags=portal-instance-<id>&size=1000` (follow `next`), `GET /key-auths?tags=portal-instance-<id>` | read |

**Create app (`POST /v1/apps`), AC 6 and 8:**
1. Validate the body. Load the `apiIds`; every one must be published, or return 404.
2. Generate `appId`, `credId` and the key (`pk_` + base64url of 32 bytes from `crypto.randomBytes`).
3. Call `ensureConsumer`, then `issueCredential`.
4. In one Postgres transaction, insert `apps`, `subscriptions`, `gateway_consumers` and
   `credentials`.
5. Return 201 with the key.

If step 3 or 4 fails:
- Call `deleteConsumer(appId)` as best-effort compensation. If that fails too, log it at warn
  level with `appId` and no key.
- Map the error: gateway → 503 or 502; unique violation on name → 409.

Kong down at step 3 means nothing is created anywhere. A retry generates new IDs and creates
exactly one consumer. If compensation fails, the reconcile job removes the orphan consumer
within 5 minutes; it carries no key the developer ever saw.

**New key:** call `issueCredential` with new IDs, then insert. If the insert fails, call
`revokeCredential` as compensation.

**Revoke (AC 9):**
- If the credential is already revoked, return 204.
- Otherwise call `revokeCredential` in Kong, then set `status = 'revoked', revoked_at = now()`.
- If Kong fails, return 503 and leave the row `active`.

Kong applies the delete immediately in DB mode, so the next proxied call with the key gets 401.

**Reconcile job (`gateway-reconcile`, pg-boss, at startup and every 5 minutes, singleton):**
- List the instance-tagged consumers. Delete any whose `custom_id` has no `apps` row.
- List the instance-tagged key-auths. Delete any whose credential row is `revoked` or missing.
- For an `active` row whose Kong credential is missing, log `drift` at warn level. Don't
  re-create it, because the portal doesn't have the key.

**Try-it proxy:** see ADR 0003.
- Load the published APIs' `gatewayBaseUrl` set into an allowlist (cached 30 s).
- Require `scalar_url` to start with one of them on a path-segment boundary.
- Rewrite it to `KONG_PROXY_INTERNAL_URL`.
- Forward these headers: `apikey`, `accept`, `content-type`, `content-length`, and any header
  named in the API document's apiKey schemes. Drop all others.
- Use `fetch` with `redirect: 'manual'`.

### Risks and how to test them
| Risk | Mitigation | Test |
| --- | --- | --- |
| Quickstart takes over 5 minutes while images are built locally | Next.js `standalone` output, multi-stage Dockerfiles with pnpm `fetch` cache layer, GHCR images once named | CI job `compose-smoke`: `docker compose up -d --wait` then `curl :3000` and Playwright smoke; record the wall time in the test report |
| Kong 3.9 is the last OSS image line | Pin `kong:3.9`; adapter uses only long-stable Admin API endpoints | Testcontainers integration suite runs against the pinned image |
| `PUT /consumers/{c}/key-auth/{id}` upsert behaves differently across Kong versions | Conformance test asserts that calling twice with the same id gives one credential | `adapter-kong` integration test |
| Orphaned Kong objects after partial failure (AC 8) | Compensation + reconcile job + instance tag | Integration: Kong stopped → `POST /v1/apps` = 503, zero apps, zero tagged consumers; Kong started → retry = 201, exactly one tagged consumer. Unit: credential call fails after consumer upsert → consumer deleted |
| Try-it proxy abused as an open proxy / SSRF | Published-API allowlist, header allowlist, no redirects, 1 MiB caps, rate limit | Unit tests for allowlist bypass attempts (`..`, `@`, prefix tricks like `/sample-evil`, other hosts) |
| Import by URL reaches internal hosts | Admin-only, http(s) only, 10 s, 5 MiB | Unit tests for scheme and size limits |
| Any portal key works on every key-auth Kong service | Documented in ADR 0002; per-API ACL groups come in the plans spec | Not tested in this slice (known limitation, noted in README) |
| Key leaks to logs | Fastify logger redaction for `key`, `apikey`, `authorization`, `cookie`, `*.password`; key never persisted | Unit test: create-app log output contains no `pk_` |
| Default secrets used in production | Refuse to boot with dev defaults when `NODE_ENV=production` | Unit test of config loader |

## UX  _(ui-designer)_
Full design: [docs/design/001-kong-quickstart-slice.md](../design/001-kong-quickstart-slice.md).
Tokens: [docs/design/tokens.md](../design/tokens.md) (new; one light theme, CSS variables
with shadcn names, mapped onto Scalar's variables).

- **Flows:**
  - A: catalog → reference → sign up (`next` kept) → create app (API preselected) → key
    shown once → back to the reference to try it.
  - B: admin import and publish.
  - C: revoke a key.
  - D: gateway unavailable on create app, then retry.
  - E: additional key.
- **Screens:** catalog `/`; API reference `/apis/[slug]` (header strip with base URL, "Get an
  API key" and a one-line try-it hint above Scalar); sign-up and sign-in; dashboard with
  an onboarding empty state; create app; app detail with keys table and "Try your key"
  panel; admin `/admin/apis` (import form plus published list). Each screen has
  ASCII wireframes at 375px and 1280px and covers loading, empty, error, success and
  no-permission states.
- **Key handover (AC 6):** `KeyRevealDialog` is an alert dialog. It can only be closed with
  "I've saved it", gives a Copy button with "Copied" feedback, and shows the header name.
  The key is kept in memory only and never goes in a URL or storage.
- **Errors:** every problem type in the contract maps to specific copy. A 503 keeps the
  form, says "Nothing was created" and shows a "Try again" countdown driven by `Retry-After`
  (AC 8). A 422 invalid OpenAPI shows the problem `detail` verbatim plus "Nothing was
  published" (AC 4). Revoke failures keep the key shown as Active.
- **Components:** shadcn/ui throughout. New components: `PageHeader`, `EmptyState`,
  `CopyButton`, `CodeValue`, `KeyHint`, `StatusBadge`, `ProblemAlert`, `KeyRevealDialog`,
  `ApiCard`, `GatewayServiceOption`.
- **Accessibility:** targets WCAG 2.2 AA. The doc gives the keyboard path for flow A, the
  focus rules, the labelling and live regions, and checked contrast ratios.
- **Responsive:** tables become cards at 375px, the header nav moves into a Sheet, and
  form actions go full width.
- **For the backend (optional):** the design suggests `detail` strings for the try-it
  proxy problems, because Scalar shows them as-is (design §6).

### Blocking
1. **JSO-185: reconcile and seed job failures still aren't logged.** `apps/server/src/startup.ts:109-114`.
   `boss.on('error')` at `startup.ts:99` doesn't receive handler failures: pg-boss 10.4.2 catches
